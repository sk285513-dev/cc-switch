## 使用原則

RAGFlow 的檢索品質，不是只靠向量資料庫本身，而是來自 **chunking、hybrid search、keyword 權重、top N、rerank** 的整體配置。對 16G VRAM 的本地系統來說，應該優先用 RAGFlow 內建 / 官方相容後端，先把資料分型與檢索參數調好，再考慮更重的基礎設施。[web:2379][web:2377][web:2381]

RAGFlow 本身在聊天檢索時就會同時做 **full-text + vector 的多重召回**，因此在設定知識庫之前，應先依資料類型做不同切塊與參數策略，而不是把所有資料都用同一套規則硬套。[web:2383][web:2324]

## 1. 研究筆記

### 資料特性

研究筆記通常是比較長的段落、概念說明、比較分析或架構決策紀錄。這類資料若切太碎，容易失去論證上下文；若切太大，又會讓召回結果混入太多不相關內容。[web:2323][web:2383]

### 建議設定

- Chunking：中到大塊，以段落群組為單位，保留 1–3 段的概念完整性。  
- Similarity Threshold：0.15–0.25。[web:2377]  
- Keyword Weight：中等，因為研究筆記兼具語意與少量術語。  
- Top N：6–8。[web:2377]  
- Rerank：建議開啟，因為研究問題通常需要更好的相關性排序。[web:2377][web:2380]

### 適合的查詢

- 「比較 RAGFlow 與 R2R 的差異」
- 「過去對本地研究型 AI 架構的決策理由」
- 「之前寫過哪些關於混合檢索的筆記」

## 2. 程式碼 / Log / Bug 紀錄

### 資料特性

這類資料最怕切得太大，因為一個錯誤碼、函式名、路徑、stack trace 往往就決定了檢索精度。對 coding 與除錯場景來說，**keyword matching 的重要性通常高於純語意相似度**。[web:2377][web:2380]

### 建議設定

- Chunking：小塊；以函式、class、錯誤段落、log 區段為單位。  
- Similarity Threshold：0.10–0.20。[web:2377]  
- Keyword Weight：高，尤其對錯誤碼、檔名、函式名。 [web:2377]  
- Top N：4–6。[web:2377]  
- Rerank：可視情況開啟；若是快速 debug 查詢，可先關閉以換取速度。 [web:2377]

### 補充策略

- log 應按時間段或錯誤區段切塊。  
- code 應盡量避免跨函式切塊。  
- 長 stack trace 可做摘要版與原始版雙軌保留。

### 適合的查詢

- 「之前哪個 patch 修過相同的 error」
- 「這個 stack trace 對應到哪個模組」
- 「專案內哪些地方提過 host.docker.internal」

## 3. 法律資料

### 資料特性

法律資料包含法條、判決、裁定、契約條款、書狀草稿等，通常具有強烈結構性與專有名詞密度。這種資料很不適合粗暴的大段切塊，因為一旦跨條或跨段，引用與論證就容易失真。[web:2383]

### 建議設定

- Chunking：依條、款、項、段切；不要跨條拼接。  
- Similarity Threshold：0.10–0.18。[web:2377]  
- Keyword Weight：高，因為法條編號、案號、爭點詞非常重要。[web:2377]  
- Top N：6–10。[web:2377]  
- Rerank：強烈建議開啟，因為法律檢索很需要重排以減少表面相似但實質無關的片段。[web:2377][web:2380]

### 補充策略

- metadata 應保留：法源、日期、法院、案號、條號、關鍵爭點。  
- 判決摘要與原文可分開 ingest。  
- 法條與實務見解應分資料集管理，再於 query 階段整合。

### 適合的查詢

- 「找與強制執行異議之訴相關的條文與見解」
- 「過去筆記裡如何整理某條法規的爭點」
- 「這份書狀草稿對應到哪些法條與判決」

## Chunking 補充建議

| 資料型態 | 不建議做法 | 建議做法 |
|---|---|---|
| 研究筆記 | 每 200 字硬切 | 依標題 / 子題 / 段落群組切 [web:2323] |
| 程式碼 | 跨函式切塊 | 以函式 / class / log 區段切 |
| 法律資料 | 多條法規合併一塊 | 依條、款、項、段切，保留來源 metadata |

RAGFlow 強調 deep document understanding 與語意切塊能力，因此真正有效的做法，是讓 chunk 盡量對應「人類理解的一個完整單位」，而不是單純按字數切。[web:2324][web:2323]

## v1 建議的統一策略

若你現在先想用一套可以上手的 v1 設定，建議如下：

- Hybrid Search：一律開啟。[web:2383]  
- Rerank：研究筆記與法律資料開；程式碼查詢視速度需求決定。[web:2377]  
- Chunking：按資料型態分規則，不共用。  
- Top N：預設 6，再依資料型態微調。[web:2377]  
- Keyword Weight：對術語密集型資料（程式碼 / 法律）提高。 [web:2377]

## 最後的實作順序

1. 先把知識庫分成三類資料集：研究筆記、程式碼 / log、法律資料。  
2. 每類單獨設定 chunking 規則。  
3. 先開 hybrid search，再調 similarity threshold。 [web:2383][web:2377]  
4. 問 10–20 個真實問題做 retrieval test。 [web:2383]  
5. 覺得召回夠了，再決定 rerank 是否常開。 [web:2377]

這樣比先急著換向量資料庫，更能直接提升你本地研究型 AI 的可用性。[web:2379][web:2381]
