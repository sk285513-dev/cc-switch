第一部分：實際發現的問題與修復（20 條）
引擎與配置類
[致命] 引擎層級誤判：run_workflow.process_active_tasks 用頂層 config.get("stt_engine") 讀引擎，但 config.yaml 實際放在 settings: 底下，永遠讀到預設 "gemini" → Vertex-only 環境仍錯誤啟動 QuotaManager。已新增統一配置層 workflow_helper.get_engine_setting()（settings → api → 頂層），run_workflow 與 stt_runner 一律經此讀取。

config.yaml 讀取硬化：load_config() 改 utf-8-sig + errors="replace"，YAML 解析失敗回傳 {} 不再拋例外（鐵律 4）。

Manifest 競態類
[致命] 無鎖讀改寫：run_workflow 與 stt_runner 對 task manifest 的 open→json.load→改→atomic_json_dump 全部替換為 ManifestManager / update_manifest（file lock + thread lock 鎖內完成），消除「STT 剛回退 chunked/pending 又被 workflow 舊記憶體覆寫成 failed」等覆蓋災難。

failed 覆寫防護：新增 _safe_mark_task_failed()——寫 failed 前鎖內重讀；若已是 chunked+stt=pending、merged、completed 或 failed_validation_* 一律跳過覆寫，且只增改 status/error 欄位，不刪 paths / degraded_reason / merge_mode / needs_review。

completed 收斂防護：任務完成不再無條件蓋 status="completed"，鎖內重讀後保留 formatter 寫入的 failed_validation_* 驗收狀態。

chunks manifest 同等鎖防護：manifest_writer_thread 改經 ManifestManager 寫入；STT 失敗後的「failed→pending 重置」也改為鎖內讀改寫，不再用舊記憶體清單覆蓋 writer 的最新狀態。

[致命] writer 假死病灶：原 manifest_writer_thread 例外時不會對已取出的佇列項目 task_done()，導致 queue.join() 永久卡死（Chunk 產出歸零假象）。已用 try/finally 保證每筆必 task_done。

併發與調度類
嚴格分相位調度：每輪只處理一類任務——有 chunked（含 transcribed/merged 等中途態）就只跑 Phase B（KPI 自適應並發），否則只跑 queued 的 Phase A（PREPROCESS_CONCURRENCY=3）；queued 不再蹭 STT 高並發。時段硬編碼（16:00 判斷）移除，改純狀態驅動。

終止狀態隔離：completed / failed / needs_review / hold / failed_validation_* 不再進入 active batch；硬編碼 task ID 黑名單註解已刪除。

as_completed 逾時（V3 漏洞 1 對位）：batch 等待加 timeout=1800s，逾時僅記錄未回報任務並放行主執行緒，絕不強制回收金鑰；Worker 端 API 硬性逾時保證執行緒有界收斂。

金鑰與 API 類
[V3 漏洞 1] 金鑰身分核對釋放：run_single_task_safe 以局部變數 key_for_release 記錄本執行緒取得的金鑰，finally 只釋放該值；Vertex 哨兵 __VERTEX_AUTH__ 不進入釋放流程；呼叫方預傳的 key 由呼叫方釋放。殭屍執行緒甦醒無法毒化 QuotaManager。

[鐵律 9] 429 用請求當下金鑰：process_single_chunk 每輪記錄 request_key（實際發出請求的局部變數），429 時以它通報 qm.handle_error，不再抓可能已被其他執行緒換掉的 current_key_ref[0]；換 key 後強制重建 client 與上傳內容。

[鐵律 6] API 硬性逾時保留：_call_with_timeout（daemon thread + Event.wait）包住 transcribe 呼叫（150s），Vertex/Gemini 無聲掛起一律轉為 TimeoutError 進入既有 retry。

[鐵律 10] 退避五大死角補齊：503 分支原本 retry_count>=3 後不睡眠直接空轉（busy loop），已改為每次必睡（退避表+抖動）；一般錯誤分支新增 5s×retry+抖動 緩衝；Vertex 429 退避加上限與抖動；最終失敗必推播 failed 狀態；retry_count 全程累加。

acquire/release 對稱：run_stt 只釋放自己取得的 key（key_acquired_here），QuotaManager 初始化失敗降級不崩潰。

編碼與 I/O 類
[鐵律 11] ensure_ascii=True：全部 JSON 寫入（manifest、chunks、kpi_state、quota_state、api_keys_state、chunk 轉錄 json、蒸餾資料）由 ensure_ascii=False 改為 True，並統一 utf-8-sig + flush + fsync + os.replace + PermissionError 指數退避抖動。

[V3 漏洞 2] .tmp 清道夫：三處 atomic_json_dump 與 ManifestManager.write 全部加 finally 清理，任何失敗路徑不留 .tmp 殘骸。

[鐵律 7] 10106 防護：所有 import 階段的 sys.stdout.reconfigure 移除，改為 safe_reconfigure_stdio() 僅在主入口（main / _main_）呼叫且容忍 stdout=None；print、faulthandler.enable、logging StreamHandler 全部加 pythonw 防護；logging.basicConfig 在 stdout 為 None 時只掛 FileHandler。

[鐵律 4/5/12] 讀檔與日誌：所有讀檔加 errors="replace"；字典取值全面 .get()（含 manifest["steps"]、chunk["path"] 等硬索引）；log_workflow/log_error 將多行訊息（含 Traceback）合併單行後一次寫入，並加執行緒鎖防交錯；_steps_start 未定義即被 except 引用的 NameError 已修。

V3 老化排序類
[V3 漏洞 2+3] 半衰期老化排序：新增 calculate_effective_priority()——1.0 + (base-1.0) * math.exp(-0.1 * wait_hours)，等待時間取自 manifest payload 的 created_at（掃描時自動鎖內補寫，絕不信任 os.path.getctime，防「返老還童」）；分數永不塌破 1.0，科目優先序鐵律不崩壞，舊任務漸進防餓死。

重要跨批次相依提醒

V3 Peer Review 報告點名的 safe_acquire_key / force_reclaim / as_completed(timeout=600) 在實機原始碼中不存在（已全文檢索確認），本批以等效防線對位實裝，未憑空修補幻影函數（鐵律 13）。
