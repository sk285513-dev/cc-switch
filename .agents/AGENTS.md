# LexMind-Omni 專案最高優先遵守規矩 (Priority Rules)

本文件定義了本法律實務 AI 工作站執行所有影音轉譯與講義生成專案時的最高指導原則與品質驗收標準。所有 AI 代理人與執行緒必須無條件優先遵守此規範。

---

## 📂 一、 本地端（Local）的任務分工：重度 I/O 與影音預處理
本地端主要負責高硬體消耗、大檔案讀寫、以及圖像特徵偵測等不需要強大語言邏輯，但極度消耗 CPU/GPU 運算資源 of 底層操作：

1. **音訊提取與規格轉換 (FFmpeg / 本地 CPU)**：
   * 動作：直接讀取數 GB 的原始 MP4 影片，快速提取音軌，並降採樣為標準 16kHz 單聲道 WAV 格式，減輕後續上傳雲端的流量負擔。
2. **智慧靜音切片 (Silence Detection / 本地 CPU)**：
   * 動作：利用本機 CPU 分析音訊波形，偵測大於 1.5 秒 且低於 -35dB 的靜音點，在老師說話的斷句邊界進行切片（限制在 12 分鐘 內），避免粗暴切斷句子影響雲端語意理解。
3. **影像偵測與板書裁剪 (OpenCV / 本地 GPU/CPU)**：
   * 動作：本地以每秒 1 幀（1fps）的高頻率掃描影片，利用圖像差分法（Frame Difference）判斷老師何時在黑板上寫字，在畫面穩定後進行螢幕去噪、投影校正，並裁剪出乾淨的板書區域圖片，存放在本機快取。
4. **向量資料庫與混合檢索 (Qdrant & BM25 / 本地 Docker)**：
   * 動作：在本地部署 Qdrant 容器。本地計算稀疏向量（BM25 關鍵字統計）與混合檢索（Hybrid Search），保障檢索的即時性。

## ☁️ 二、 雲端（Cloud）的任務分工：高階語意理解與視覺 OCR
雲端主要調用 Gemini 2.5 Flash / Pro 大模型，負責語音聽寫、上下文同音錯字校對、大綱摘要、以及複雜圖表視覺解析：

1. **分片語音轉寫 (STT / Gemini 2.5 Flash)**：
   * 動作：將切好的 12 分鐘 WAV 音檔上傳至 Gemini Files API，由 72B 級別的語音多模態能力直接進行聽寫。
   * 優勢：在聽寫的第一步，就透過雲端強大的法律知識庫，將口語贅字過濾，並直接將同音錯字（如把「地政士」聽成「遞贈式」）在源頭校正。
2. **圖像板書視覺翻譯 (Visual OCR / Gemini 2.5 Flash)**：
   * 動作：將本地 OpenCV 提取的乾淨板書圖片上傳，由 Gemini Flash 進行多模態識別，將黑板上的圖畫、複雜法律關係圖表（如：甲→乙→丙的侵權行為關係）翻譯成結構化的 Markdown 文字筆記。
3. **全文語意精校與拼接 (Merge & Refinement / Gemini 2.5 Pro)**：
   * 動作：將所有分片的逐字稿拼接，由擁有超大上下文的 Gemini Pro 閱讀全文，進行跨片段的語意流暢度微調，並自動生成整堂課的「精準章節大綱」與「核心爭點摘要」。
4. **講義與板書深度融合 (Final Formatter / Gemini 2.5 Flash)**：
   * 動作：比對板書圖片的時間戳記與逐字稿時間戳記，將「板書筆記」插入到逐字稿的對應段落中，渲染出最終排版精美的 Markdown 筆記。

## ⚖️ 三、 系統技術與品質驗收標準 (Acceptance Criteria)

### 1. 檔案落地與實體存在性標準 (Physical Deliverables)
任務狀態標記為 `completed` 後，以下檔案必須確實、完好且持久地保存在 `A:\processed_md\` 中，**且同時自動複製一份備份至影片原始存放目錄（如 `J:\土地登記\ch1\` 等）**：
* **`[課程名稱].md`**：最終精校 Markdown 講義（包含逐字稿、階層大綱、以及黑板板書筆記）。
* **`[課程名稱].srt`**：標準繁體中文 SRT 字幕檔。
* **`[課程名稱].vtt`**：標準 WebVTT 字幕檔。
* **`[課程名稱].txt`**：純文字逐字稿（去除時間戳記與口語贅字，供純文字閱讀）。
* **`[課程名稱]_index.json`**：包含段落索引、主題摘要的結構化 JSON（供後續 Qdrant 向量資料庫檢索）。
* *註：在 Windows 檔案總管與終端機（PowerShell / cmd）下執行 dir，必須能直接列出並正常開啟這些實體檔案。*

### 2. 講義內容與法律專業品質標準 (Content Quality)
文字與格式必須達到台灣法律實務的嚴格標準（正確率 >= 98%）：
* **贅字過濾**：100% 過濾講師的口語贅字（如「那個」、「然後」、「就是說」、「嗯」、「啊」），句型通順。
* **消滅同音錯字**：所有台灣法律學術與實務術語必須精準辨識，不得出現同音錯字。
  * *錯誤範例*：格論、地政治、消滅實效、借名登記（寫成同音字）。
  * *正確範例*：各論、地政士、消滅時效、借名登記。
* **法條與字號格式標準化**：
  * 所有法條條號必須標準化（如：民法第一百九十七條 或 民法第197條、行政程序法第131條）。
  * 釋字與判決字號必須標準化（如：釋字第474號解釋、最高法院49年台上字第1730號民事判例）。
* **Markdown 結構化排版**：
  * 必須依課程主題切換，主動劃分 Markdown 標題階層（#、##、###）。
  * 必須在關鍵段落自動加上重點粗體標記（如：`**【爭點】**`、`**【實務見解】**`、`**【核心結論】**`）。

### 3. 板書影像偵測與 OCR 整合標準 (Blackboard & Visual Integration)
* **板書擷取準確度**：本地 OpenCV 必須精準捕捉講師在黑板前寫字的畫面，在畫面變更且穩定時才進行截圖，避免產生重複或模糊的冗餘影格。
* **影像視覺解析（OCR）**：Gemini 必須正確將黑板上的手寫字、複雜法律法律關係圖（如：甲→乙→丙的代理、侵權、不當得利關係）翻譯成結構化的 Markdown 文字筆記。
* **時戳精準嵌合**：板書翻譯筆記必須在正確的時間點插入 `.md` 講義的逐字稿段落中，不得有時間軸錯位。
* **Obsidian 聯動**：板書圖片與個別解析檔案需正確保存於 C 碟的 `Obsidian_Vault/04_教材圖表校對/`。

### 4. 系統運行與防碰撞安全標準 (System Reliability)
* **429 容錯與金鑰池輪替**：在遭遇 Gemini 雲端 API 頻率限制（429 Too Many Requests）時，Worker 不能崩潰退出，必須自動進行自適應睡眠退避（抓取 API 回傳的精確秒數進行 cold down），並在同一個分片連續失敗 3 次後自動輪替至金鑰池中的下一把金鑰。
* **進度即時存檔**：每完成一個切片的轉寫，必須立刻將 chunks manifest 寫回磁碟存檔，確保系統異常中斷後能無縫接續進度，絕不重複消耗 API 額度。
* **記憶體與硬體安全守護**：
  * CPU 負載均衡，不發生 100% 暴衝假死。
  * 本機 GPU 顯存（VRAM）不溢出。
  * 顯卡溫度必須守在 78°C 的安全閾值之下（超溫自動降載或暫停）。
* **原始切片永久備份 (禁止刪除)**：單個任務順利完成（completed）後，【絕對禁止】刪除 A 碟 chunks 底下的切片暫存。必須由 markdown_formatter.py 自動將整個資料夾（包含 .wav 與 .txt）安全搬移至 F:\chunks_backup\（若容量小於 50GB 則備援至 E:\chunks_backup\），以保留免 API 重做之能力。

## 🛡️ 七、 LexMind-Omni 核心防護原則與開發禁令 (Core Safeguards & Bans)
根據前代技術文件，為避免代理人重複犯錯或破壞系統，所有執行緒必須嚴格遵守以下禁令與原則：

1. **視窗代碼輸出禁令 (No Large Code Blocks in UI)**
   * 嚴禁在聊天對話視窗輸出超過 50 行的完整程式碼區塊，防止 KV Cache 爆炸。
   * 所有程式碼變更必須靜默呼叫原生檔案寫入工具 (replace_file_content / multi_replace_file_content 等) 處理。
2. **Git Rollback 紀律 (Bug Fix Protocol)**
   * 若連續 3 輪除錯 Bug 未減或發生錯誤漂移，必須執行 Git Rollback 退回最近的安全綠色節點，重新審視底層問題，禁止繼續堆疊補丁。
3. **時效敏感性原則 (Deadline Calculation)**
   * 涉及消滅時效、除斥期間的計算必須使用系統的 DeadlineCalendar 知識庫，禁止 LLM 自行計算時效。
4. **幻覺防護與引用完整性 (No Hallucinated Citations)**
   * 嚴禁直接輸出未經查證的法律引用。所有生成的法律文本必須附帶可驗證的條文引用，禁止使用「依相關法規」等模糊表述。
5. **中文路徑處理 (UTF-8 Path Encoding)**
   * 所有 Node.js/Python 腳本呼叫必須使用 execFile 而非 exec，確保透過 Windows Unicode API（CreateProcessW/UTF-16）傳遞路徑，避免 CP950 字元集破壞中文路徑。
6. **資料最小化原則 (Data Privacy)**
   * 日誌中禁止記錄姓名、身分證字號、案件當事人等敏感資訊，統一以 [REDACTED] 替代。

## 💽 十、 檔案與磁碟掃描防護禁令 (Drive & Extension Safeguards)
為防止 `auto_ingest_bot.py` 或任何負責處理課程的模組發生「無差別全機掃描」導致吃進不相關個人檔案或消耗資源，**所有代理人在修改或建立掃描腳本時，必須嚴格遵守以下兩點死命令**：

1. **掃描磁碟白名單解鎖 (Full Drive Whitelist)**：
   * 系統**允許掃描本機所有有效的磁碟機 (A~Z 碟)**，以確保新課程無論下載到哪裡皆能被自動發掘。

## 💻 十一、 終端機與腳本語法強制規範 (Strict PowerShell Syntax Rule)
為避免使用者在終端機複製貼上時發生語法衝突與報錯，**所有提供給使用者直接複製執行、或用於終端機自動化的指令與腳本，必須無條件且唯一使用 PowerShell (PS) 語法。**
1. **絕對禁止**提供傳統 CMD 或 `.bat` 的語法（如使用 `::` 當註解，或是 `start "title" cmd ...`）。
2. 啟動新視窗必須使用 `Start-Process`（如 `Start-Process powershell -ArgumentList "-NoExit -Command ..."`）。
3. 註解必須使用 `#`，若需提供指令稿給使用者，一律提供 `.ps1` 的寫法，禁止要求使用者去雙擊 `.bat` 檔。
4. 任何時候都不准再假設使用者會在傳統命令提示字元 (cmd.exe) 執行指令，全面封殺 cmd 語法，避免惹惱使用者。

## 🛑 十二、 嚴禁「自作聰明重造輪子」與腳本覆蓋禁令 (No Reinventing the Wheel)
為避免浪費使用者寶貴的 API 額度與對話時間，所有 Agent 必須嚴格遵守以下「不重造輪子」鐵律：
1. **先尋找原版程式碼，絕不盲目新建**：當使用者提到「一鍵啟動」、「啟動腳本」或任何已存在的自訂功能時，Agent **必須先**在工作站目錄（`C:\LocalAI_Workstation\`）確實搜索（Grep / List Dir）原版腳本，或請使用者提供原版程式碼。
2. **禁止擅自曲解使用者意圖**：過去曾發生極為嚴重的致命錯誤——Agent 將使用者的「LexMind-Omni 引擎與面板一鍵啟動腳本」（內含 Dashboard/KPI Runner、Watchdog 及 Node.js UI 伺服器）誤解為單純的「Log 監控 tail 視窗」，並擅自寫了毫無用處的假腳本去取代真腳本，導致系統癱瘓且嚴重惹惱使用者。
3. **無授權禁止覆蓋**：任何涉及環境啟動、伺服器配置與排程的腳本，若未取得使用者原版真跡，**絕對禁止**發揮自己的想像力去重寫或覆蓋。不會就問，找不到就請使用者貼上來，嚴禁「猜測」與「自作聰明」！

## 🛠️ 十三、 最小化修改與禁止過度工程 (Minimal Edit & No Over-Engineering)
為避免浪費 API 額度與使用者的除錯時間，**任何未來接手此專案的模型在修改使用者提供的程式碼前，必須強制閱讀並遵守本條例**：
1. **直接給出差異，禁止自作聰明寫包裝腳本**：當使用者貼出一段原版腳本並指出某一行有問題時，Agent 必須「乖乖地」只針對有問題的那一行進行修正，並把「修改後的完整程式碼」直接貼回對話框讓使用者複製。
2. **嚴禁過度工程 (No Over-Engineering)**：絕對禁止為了一個簡單的 PowerShell 單行語法修正，就擅自跑去寫一個 Python 或 VBS 包裝腳本來重新產生該檔案。這種「把簡單問題複雜化」的行為不僅極度浪費資源，且極易引發字元跳脫或引號解析的二度災難。
3. **不要炫技**：使用者只要「對的結果」，不要 Agent 裝厲害搞出一行指令或各種華麗但不穩定的背景黑科技。回歸最基礎、最穩定的直接修正法！

## 🧠 十五、 2026-07-16 血淚反省：徹底根絕「假會、不看備份污染、與無視編碼」的三大愚蠢行為
為了徹底防止未來的 AI Agent 再次浪費使用者的時間，必須將今日的教訓刻入基因，任何代理人若再犯以下錯誤，即視為最嚴重的失職：
1. **備份污染盲點 (Backup Taint Blindspot)**：
   * 當使用者在規則中明確指出「過去的 AI 寫了錯誤的假腳本（例如把儀表板變成純 Log 視窗）」時，**絕對不要**跑去讀取舊日期的備份檔（如 7/13），然後把那個「已經被前一個 AI 寫壞的錯誤腳本」當成真理重新還原給使用者！
   * **鐵律**：歷史備份檔裡面可能已經包含了被污染的錯誤程式碼。必須用「邏輯」去判斷腳本內容是否符合使用者的真實需求（如呼叫 Python 儀表板），而不是盲目相信檔名。
2. **無視系統底層編碼 (Ignoring Encoding Realities)**：
   * 已經在規則 5 與 13 反覆警告過 CP950 會破壞中文與引發語法崩潰，卻還是以「這很罕見」為藉口，用沙箱預設的 pwsh (UTF-8 無 BOM) 去寫入使用者的 .ps1 腳本。這會導致使用者在原生的 Windows PowerShell (5.1) 執行時，中文亂碼剛好破壞了引號或括號，造成 Start-Process 無聲無息地閃退。
   * **鐵律**：任何給使用者在本機執行的含有中文字元的腳本，**必須強制使用 Set-Content -Encoding utf8BOM**，絕不允許任何妥協或忘記。
3. **遇到問題先包裝，不修原代碼 (Wrapper Anti-Pattern)**：
   * 看到沙箱不能彈出視窗（Session 0 隔離），不去向使用者解釋原因或老實還原 .ps1 讓使用者自己點，反而自作聰明寫了 .vbs 去取代使用者的 .ps1 甚至擅自刪除原檔案。這完全違背了「最小化修改」原則。
   * **鐵律**：絕對禁止用「建立新包裝腳本」來逃避解決原腳本的問題。使用者要 .ps1 就給 .ps1！

## ⚠️ 十八、 專有名詞定義：「空殼切片 (completed)」的階段性釐清 (Status Terminology Rule)
為了防止未來的 AI 代理人將「任務整體的 completed」與「單一切片的 completed」混淆，甚至誤以為「所有待處理的任務都被標成了 completed」，特此嚴格定義：

1. **什麼是「空殼切片 (completed)」？**
   - 這裡的 `completed` **僅限於「雲端語音轉寫 (STT) 階段」的單一 12 分鐘切片 (`_chunks.json` 裡的單一項目)**。
   - **定義**：當 `stt_runner.py` 將切片丟給雲端模型 (如 Vertex AI) 後，模型雖然順利回傳了結果並將該切片標記為 `"status": "completed"`，但實際上回傳的 `"text"` 欄位卻是**空字串**。這就是所謂的「被毒化的空殼切片」。
2. **請勿與「任務完成 (Task Completed)」混淆：**
   - 當整個任務 (Task) 達到 `completed` 時（由 `markdown_formatter.py` 判定），代表講義與 SRT 均已完美生成，且檔案已被搬移到 `F:\chunks_backup\`。
   - 遇到大量等待重做的課程 (例如 432 堂) 時，這 432 堂課的「主狀態」通常是 `chunked` (已完成前端派工)，而它們底下成千上萬的切片多數仍是乾淨的 `pending` 狀態，只有少數被前一代崩潰的模型標成了有問題的 STT 階段 `completed`。
   - **鐵律**：AI 在分析災情時，必須精確區分 `主 Manifest 的狀態` 與 `單一切片 Chunks 的狀態`，絕不可一竿子打翻一船人，將 pending 的待處理檔案誤認為已被毒化。

## 🐢 十九、 本地開發與運作核心哲學：穩定壓倒一切 (Stability Over Speed)
1. **求穩不求快**：我們本地的工作（包含腳本修改、API 呼叫與系統併發設計）**務必求穩定而非求快**。

3. **安全邊際 (Margin of Safety)**：未來在設計任何速率限制、並發數量或重試機制時，必須預留充足的安全邊際。寧可讓系統多跑十分鐘，也絕對不允許因為追求一兩秒的快感而導致整個管線癱瘓，浪費更多的除錯時間。這點必須列為未來所有 AI Agent 的優先思考法則。
